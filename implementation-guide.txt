Purpose, outcome and scope
OpsSentinel AI demonstrates AI engineering for operational systems: log normalization, deterministic detection, evidence correlation, retrieval of historical knowledge, root-cause hypothesis generation, human-approved remediation and incident reporting. It is designed as a safe simulator and decision-support tool, not an autonomous production operations bot.
Target final outcome: A user uploads or streams sample logs, a rule creates an incident, agents identify the important events, generate evidence-ranked root-cause hypotheses, retrieve a relevant runbook, propose safe remediation, wait for engineer approval and generate a post-incident report.
MVP success criteria
Runs completely locally without paid monitoring, cloud or LLM services.
Accepts pasted text, file upload and JSON API log records.
Normalizes at least three log formats into one schema.
Detects prepared incidents using explainable rules.
Builds an immutable incident timeline and evidence window.
Outputs facts, likely cause, alternatives, missing evidence and confidence.
Retrieves one or more relevant runbooks or historical incidents.
Does not execute remediation commands automatically.
Produces an engineer-approved incident report and portfolio-quality demo.

Incident lifecycle
1.  Logs arrive through upload, paste, JSON API or a synthetic generator.
2.  Normalization maps timestamp, level, service, environment, trace ID, message and attributes.
3.  Rule engine evaluates sliding-window counts, patterns and thresholds.
4.  When a rule matches, an alert and incident are created with an evidence window.
5.  Monitoring Agent summarizes the detection and suggests initial severity.
6.  Log Analysis Agent groups errors and builds the earliest-to-latest event sequence.
7.  Security Agent examines authentication and suspicious indicators when relevant.
8.  Root Cause Agent generates ranked hypotheses using evidence and similar incidents.
9.  Runbook Agent retrieves procedures and prepares diagnostic, containment and remediation steps.
10.  Engineer approves, revises or rejects the proposed action; the platform records the actual resolution.
11.  Incident Report Agent creates a post-incident report and indexes lessons learned.
Concept catalogue with justifications
Concept: AIOps
Meaning
Application of automation and AI to operational telemetry and incident workflows.
How it is used
The project uses rules, retrieval and language models to assist detection, investigation and reporting.
Why this method is selected
It demonstrates AI outside business-document assistants and connects engineering data to accountable workflows.
Trade-off / alternative
A real AIOps platform requires production integrations and large-scale telemetry; this project is an interview MVP.

Concept: Log normalization
Meaning
Converting different raw formats into one canonical event schema.
How it is used
Regex/JSON parsers map logs to timestamp, level, service, trace ID, message and attributes.
Why this method is selected
Agents and rules should not understand every vendor-specific format. Normalization reduces downstream complexity.
Trade-off / alternative
Sending raw logs directly to the LLM is quicker but expensive, inconsistent and hard to query.

Concept: Deterministic detection rules
Meaning
Explicit conditions create alerts from known failure patterns.
How it is used
Examples include more than 10 HTTP 500 errors in five minutes or repeated database connection failures.
Why this method is selected
Rules are explainable, fast and reliable for the prepared demo. They separate detection from LLM interpretation.
Trade-off / alternative
ML anomaly detection is valuable later but needs history, feature engineering and evaluation data.

Concept: Sliding time window
Meaning
Events are counted or aggregated over a recent interval.
How it is used
Rules evaluate service errors, latency and failed logins over one- or five-minute windows.
Why this method is selected
Operational incidents are patterns over time, not isolated lines.
Trade-off / alternative
A single-event trigger is simpler but creates noisy alerts.

Concept: Event correlation
Meaning
Related events are joined using time, service, trace ID and dependency clues.
How it is used
Database timeout events are associated with subsequent API 500 errors and latency changes.
Why this method is selected
Correlation turns a large log set into a coherent incident story.
Trade-off / alternative
LLM-only chronological summarization may miss explicit service or trace relationships.

Concept: Evidence window
Meaning
A frozen subset of telemetry around detection time.
How it is used
The incident stores pre-trigger and post-trigger log references.
Why this method is selected
It preserves what the analysis was based on and prevents later log changes from silently altering the conclusion.
Trade-off / alternative
Always querying live logs can be useful in production but weakens reproducibility.

Concept: Root-cause hypothesis
Meaning
A ranked explanation that remains distinct from confirmed fact.
How it is used
The RCA output labels facts, likely cause, alternatives, contradictions and missing data.
Why this method is selected
This avoids presenting plausible language as certainty.
Trade-off / alternative
A single definitive cause is easier to read but unsafe when evidence is incomplete.

Concept: Evidence scoring
Meaning
Candidate causes are ranked by supporting events, contradictions and coverage.
How it is used
Deterministic code scores whether each hypothesis explains the first failure, affected services and observed recovery.
Why this method is selected
It creates a transparent reason for ordering hypotheses instead of trusting model confidence alone.
Trade-off / alternative
Pure LLM ranking is less reproducible.

Concept: Runbook
Meaning
A documented procedure for diagnosis, containment and recovery.
How it is used
Runbooks are stored, chunked and retrieved for the affected service and symptom.
Why this method is selected
Operational knowledge should be reused rather than generated from scratch for every incident.
Trade-off / alternative
Generated steps without runbook retrieval may be generic or unsafe.

Concept: Human approval gate
Meaning
An engineer authorizes the operational action.
How it is used
The system shows commands and risks but never runs them in the MVP.
Why this method is selected
Commands can destroy data or worsen outages. Approval is the correct safety boundary.
Trade-off / alternative
Autonomous remediation is a future capability only after sandboxing, permissions, rollback and extensive testing.

Concept: Immutable timeline
Meaning
Incident events are appended rather than rewritten.
How it is used
Detection, analysis, decisions, remediation and validation are timestamped.
Why this method is selected
It provides accountability and creates high-quality post-incident reporting data.
Trade-off / alternative
Editable notes are convenient but can erase the sequence of decisions.

Concept: Severity model
Meaning
A consistent classification of operational impact.
How it is used
SEV-1 to SEV-4 combines affected users, criticality, duration and workaround availability.
Why this method is selected
Severity determines response expectations and prioritizes the dashboard.
Trade-off / alternative
Letting the LLM invent severity with no policy produces inconsistent incidents.

Concept: Knowledge-base RAG
Meaning
Historical incidents and runbooks are retrieved to ground recommendations.
How it is used
pgvector returns similar incidents filtered by service, symptom and environment.
Why this method is selected
It improves specificity and demonstrates organizational learning.
Trade-off / alternative
Fine-tuning is unnecessary because the knowledge changes and needs citations.

Concept: Safe tool boundary
Meaning
Agents only access approved read or proposal tools.
How it is used
The MVP provides database reads, retrieval and deterministic calculators, but no shell execution.
Why this method is selected
Tool limitations are a fundamental agent-safety control.
Trade-off / alternative
A general shell tool looks impressive but introduces unacceptable risk on a personal laptop.

Concept: Local inference
Meaning
Models run through Ollama on the laptop.
How it is used
Qwen3 4B performs analysis and nomic-embed-text performs retrieval embeddings.
Why this method is selected
It meets the free requirement and avoids external transfer of operational data.
Trade-off / alternative
Hosted models may improve quality but add cost and data-governance considerations.

System and agent architecture

OpsSentinel AI logical system architecture
Architecture justification
Hybrid deterministic and generative design: Rules decide when an incident exists; the LLM interprets evidence and drafts recommendations. This places reliability before novelty.
Modular monolith: One FastAPI application is appropriate for a three-day build and a laptop. Parser, detection, incident and AI packages remain separate inside the codebase.
Database-centric event history: PostgreSQL stores logs, alerts, incidents and timeline records. This is easier to inspect than hiding state in agent memory.
Local knowledge base: Runbooks and resolved incident reports are embedded into pgvector, allowing the project to demonstrate organizational learning.
No command executor: The remediation layer returns proposed commands and validation steps. This is a deliberate security architecture decision.

Log ingestion, detection and event correlation
Canonical log event schema
{  "event_id": "uuid",  "timestamp": "2026-07-21T10:03:14.231Z",  "received_at": "2026-07-21T10:03:15.002Z",  "service": "checkout-api",  "environment": "demo",  "level": "ERROR",  "message": "database connection timeout",  "trace_id": "trc-82af",  "host": "checkout-01",  "source_type": "application",  "attributes": {    "http_status": 500,    "latency_ms": 5200,    "database": "orders"  },  "raw_line": "...",  "parse_status": "parsed"}
Parser strategy
1.  Attempt JSON parsing first and map known keys.
2.  Attempt key=value parsing for structured text.
3.  Attempt a configured regex format for timestamp, level, service and message.
4.  If parsing is incomplete, preserve raw_line and set parse_status=partial rather than discarding the event.
5.  Normalize time zones to UTC while preserving the original timestamp string.
6.  Generate a stable event hash to prevent duplicate ingestion.

Why rules create incidents before agents run
An LLM should not continuously read every log line on a laptop or decide incident existence from vague prompts. Rules are cheap, explainable and testable. Agents run only after a meaningful condition is detected, which limits latency, model load and false narratives.

Root-cause analysis and knowledge retrieval

Evidence-ranked root-cause analysis model
RCA output model
{  "confirmed_facts": [    {"statement": "Database timeouts began at 10:03:14Z", "event_ids": ["..."]}  ],  "hypotheses": [    {      "rank": 1,      "cause": "Orders database connection pool exhaustion",      "supporting_event_ids": ["...", "..."],      "contradicting_event_ids": [],      "explains": ["first failure", "HTTP 500 burst", "latency increase"],      "confidence": "high"    }  ],  "missing_evidence": ["database active connection metric"],  "recommended_checks": ["inspect pool utilization and database sessions"]}
Evidence scoring example
score = 0score += 30 if hypothesis_explains_first_failure else 0score += 25 if hypothesis_explains_majority_of_error_groups else 0score += 20 if a_similar_resolved_incident_supports_it else 0score += 15 if dependency_order_is_consistent else 0score += 10 if remediation_result_later_confirms_it else 0score -= 25 for each strong contradictory event# Score is used to order hypotheses; it is not presented as a calibrated probability.
Knowledge-base ingestion
1.  Accept Markdown, text or PDF runbooks and finalized incident reports.
2.  Extract service, symptom, environment, commands, risks and validation sections.
3.  Chunk by headings such as Symptoms, Diagnosis, Mitigation and Rollback.
4.  Embed locally and store source document, section and version metadata.
5.  Filter retrieval by service and environment before vector ranking.
6.  Return citations and an explicit warning when the runbook version is old or the service does not match.

Laptop performance configuration
Ollama concurrency: Run one agent LLM call at a time initially. Parallel graph nodes can be retained logically but executed sequentially on the laptop.
Context size: Use 4K context by default. Retrieve only the top 4-6 chunks and summarize long documents before the final synthesis.
Embedding batch: Embed 16-32 chunks per batch. Persist embeddings so documents are not reprocessed on every run.
Database: Use HNSW only after data exceeds a few thousand chunks. Exact search is adequate for small sample data.
Frontend: Disable unnecessary animated charts during model execution. Poll agent-run status every two seconds rather than using WebSockets in the MVP.
Thermal stability: Use AC power and the Windows best-performance power profile for demo recordings.

Safety controls
No subprocess, PowerShell, SSH, Kubernetes or cloud SDK execution tool is registered with the agents.
Command text is displayed as untrusted proposed content and escaped in the frontend.
Destructive keywords such as DROP, DELETE without WHERE, rm -rf and shutdown trigger a high-risk badge.
Every remediation requires an authenticated engineer decision.
The actual action is recorded manually and separately from the AI proposal.
Validation evidence is required before RESOLVED can move to CLOSED.
Agent outputs cannot edit or delete timeline entries.

Interview explanation guide
The project becomes valuable only when you can defend its design. Use these answers as a framework, not as memorized marketing language.
Why use rules if this is an AI project?
Detection is a reliability problem. Rules provide explainable, testable incident triggers. AI is used where unstructured interpretation adds value: grouping errors, generating hypotheses, retrieving operational knowledge and drafting reports. This hybrid design is more credible than using an LLM for every step.
Why is the root cause called a hypothesis?
Logs rarely prove causality by themselves. The platform separates confirmed events from likely explanations and alternative causes. Resolution validation can later strengthen or weaken a hypothesis. This wording avoids false certainty.
Why not execute remediation automatically?
The MVP lacks production permissions, sandboxing, change controls, rollback automation and blast-radius testing. Displaying an approval-ready plan demonstrates responsible agent design. Autonomous execution would add risk without proving better AI engineering.
Why LangGraph?
An incident workflow must preserve state across detection, specialist analysis, retries, a human pause, resolution and reporting. LangGraph models these nodes and transitions explicitly and supports stateful, human-in-the-loop workflows [R1].
What would you add for production?
Real telemetry connectors, streaming ingestion, service topology, statistical anomaly detection, OpenTelemetry traces, RBAC/SSO, secrets management, ITSM and on-call integrations, evaluation datasets, command sandboxing, policy-as-code and high-availability deployment.
One-minute project summary
OpsSentinel AI is a local incident-response platform that ingests application logs, detects incidents with deterministic rules, correlates evidence with specialized agents, retrieves matching runbooks and produces an approval-ready remediation plan and incident report. LangGraph manages the stateful workflow, PostgreSQL stores the immutable timeline, pgvector retrieves similar incidents, and Ollama provides local language-model inference. The system deliberately does not execute remediation commands automatically; an engineer remains the decision authority.
